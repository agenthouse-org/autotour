# Plan: AutoTour 0.7.0 – manual output and capture fixes

**Status:** agreed with the product owner on 2026-11-06; implementation not started.
**Base:** `main` at 0.6.0 (00f2cff).

AutoTour is a generic, public tool. This plan names features only. Brand values, label texts, product
names and the mapping from a particular manual's needs to these features live in the consuming projects,
not here.

## Goal

A manual made of several documentation specifications can be built by `autotour run-docs` into one
self-contained, searchable HTML file per language. Its text and screenshots stay as they are, and
presentation features can be added later by upgrading AutoTour. Capture no longer needs `custom` steps
for optional clicks, after-screenshots, text conditions, navigation or asserts.

## Decisions

1. **Merge the open branches first.** The eight `cursor/*` branches from 2026-11-04/05 are rebased onto
   0.6.0, reviewed, and merged before new work. Their work records `st-15`…`st-21` clash with `ST-15`…`ST-21`
   on `main` and get new ids when merged.
2. **0.7.0 scope:** the merged branches, all HTML items in phase 2 and the capture fixes in phase 3.
   The other phases are backlog.
3. **Several apps, one manual: a manual file.** A new manual file lists documentation specifications. Each
   specification keeps its own journey and base URL. The manual orders **sections across specifications**,
   so a chapter can follow one use case through several apps ("2.1 in app A", "2.2 in app B"). One module
   still runs in one app. Switching apps inside a module (a base URL per module or step) is backlog.
4. **Ask how the manual is organised.** When an author sets up a multi-app manual, the `create-autotour`
   skill asks whether to organise it by app (one part per app) or by use case (chapters combine apps).
5. **Generic only.** Branding, labels and languages are settings with neutral defaults (English and German
   labels built in, any language can override them). No vendor-specific message formats.
6. **AI provenance hint (2026-11-06).** Text blocks, images and embedded animations can declare
   `origin: "ai-generated" | "ai-modified" | "human"`. A setting `aiDisclosure.placement` chooses
   `document` (default: a short note near the start and a closing section that lists the AI-generated and
   AI-modified content), `chapter` (a small label at each affected chapter heading) or `item` (a small
   muted label under each affected block, figure or animation). Labels are worded per language. The
   skill asks for the placement and for the origin of authored content. `validate-docs` and `run-docs` warn
   when AI-marked content exists without a disclosure setting, and when the setting is on but content has
   no declared origin. Screenshots of the real application count as `human` unless an AI changed them.
   AutoTour offers the labels; whether a publication must disclose is the publisher's decision.
7. **Navigation flavours (2026-11-06).** HTML manuals have three navigation flavours: `sidebar` (the
   default: a sticky left column with search and contents, the current section marked, collapsing behind a
   menu button on narrow screens), `topbar` (a slim sticky bar with search and a contents menu) and
   `minimal` (search and contents at the top, nothing sticky, back-to-top only). The skill asks which
   one to use and saves the choice in the project configuration (`.autotour/autotour.json`, via `configure-presentation`), and a manual file may override it.
8. **LaRecipe target in 0.7.0 (2026-11-06).** A `larecipe` documentation target writes one Markdown page
   per chapter into a version folder, generates the `index.md` sidebar, copies images to the public path,
   and renders the AI hint and callouts in LaRecipe's Markdown. Search and navigation come from LaRecipe.

Defaults chosen without a separate decision (they can be changed during review):

- Screenshots are re-encoded as WebP in the Chromium that capture already uses, so no new image library is needed. PNG is kept when WebP is not smaller.
- Anchors stay the section's `moduleId` (stable across languages). Visible numbering ("3.1") is generated.
  Number references in prose ("Chapter 3", "Section 6.2") become links through per-language patterns.
- `expect.text` without a target becomes a contains-match on the page text. With a target it stays an
  exact match. Today the target-less form can never succeed, so no working journey changes.
- A caption that would cover its target is left out with a warning instead of stopping the run, and the
  spec's `captionInImage` setting is honoured.

## Phase 2 – HTML manual (about 7–9 days)

| Feature | Acceptance | Effort |
| --- | --- | --- |
| Manual file | Lists specifications, the order of sections across them, parts, a closing glossary section, branding, labels and languages. `validate-docs` checks it, and `run-docs` builds one HTML file per language from it. A single specification without a manual file keeps working. | L |
| Image dialog | Every screenshot opens full size in a native `<dialog>`. It is focusable (`role="button"`, name "label: alt"), opens with Enter or Space, closes with Esc, the close button or a backdrop click, and returns focus to the image. It shows the caption, reuses the embedded image data, and is never printed. Embedded animations are excluded. | S |
| Search | A search field above the contents. The index covers every h2/h3 section (heading, text, captions, alt text) and is built offline in the page. Matching is case- and accent-insensitive (ß = ss through Unicode folding), and every word of two or more characters must match. Results appear in document order, at most 40, with a snippet and `<mark>`. Results replace the contents while a query is active. Enter opens the first result, Esc clears, the count is announced in `aria-live`, and labels come per language. | M |
| Back to top | A fixed button with a label per language. It appears after one viewport of scrolling, links to the top, is keyboard-focusable and visible on focus, and is not printed. | S |
| Navigation flavours | `sidebar` (default), `topbar` and `minimal` as described in decision 7, chosen in the project configuration (`.autotour/autotour.json`, via `configure-presentation`) and overridable per manual. Each one works from the keyboard and is not printed. | M |
| AI provenance hint | `origin` on blocks and `aiDisclosure.placement` (`document`, `chapter`, `item`) as described in decision 6, rendered in HTML, Markdown and PDF with labels per language, plus the validation warnings. | M |
| Parts | A part heading before a given section, also shown in the contents. | S |
| Numbering and references | Generated numbers for chapters and sections. "Chapter n" and "Section n.m" in prose link to the target, with patterns per language. | M |
| Embedded HTML block | A block embeds a local HTML file through `iframe srcdoc` with a still image. The still image stays where frames are blocked and is swapped once the embedded page posts a generic ready message. | S–M |
| Branding and draft banner | Colours, font stack, logo file and title as settings, with a draft banner that is on for drafts and off for releases. | S |
| WebP | A single file re-encodes screenshots as WebP with a quality setting, falling back to PNG when WebP is not smaller. | S |
| Print styles | Navigation, search, dialog and back-to-top are not printed, and figures are not split across pages. | S |
| LaRecipe target | `larecipe` target as described in decision 8: a version folder, one page per chapter, a generated `index.md`, images in the public path, and links between pages that work. A fixture builds and the sidebar links resolve. | M |
| Skill and docs | `create-autotour` asks how the manual is organised (by app or by use case), which navigation flavour to use, where AI hints go and where content came from. The documentation explains the manual file, the flavours, the hint and the LaRecipe target. | S |

Done when: a fixture manual with two specifications on two fixture apps, in two languages, mixing
sections across apps, builds offline into one file per language with every feature above. A browser test
covers dialog, search, back to top and the language switch from the keyboard in each navigation flavour,
and the default AI note and closing section appear when content is marked as AI-generated.

Progress (2026-11-06, branch `0.7.0-html-manual`): every feature in this table is built and tested. The
manual-file test uses two applications on separate base URLs, captured fixtures rather than live apps,
two languages and sections mixed across apps. The settings sit on the specification or on the manual, the
navigation default is saved per project, and labels are built in for English and German. The embed
block's default ready message is `{ "type": "autotour:ready" }`, and `readyMessage` can override it.

## Phase 3 – capture fixes (about 1–2 days)

| Item | Fix |
| --- | --- |
| Optional steps | Take no before-screenshot when an optional step's target is absent; skip the step. |
| After-screenshots | When the step target is gone after the action, annotate `expect.target` instead of failing. |
| Captions | Honour the spec's `captionInImage`, and leave out a caption that would cover the target, with a warning. |
| Text conditions | `expect.text` without a target matches text contained in the page; documented next to the exact form. |
| Navigation | Condition measurement retries when a navigation destroys the execution context. |
| Assert | An `assert` without its own target uses `expect.target`. |
| Hidden waits | `stableForMs` applies to `hidden`/`detached` ("absent for n ms"). |
| Target docs | Document that `{role, name}` and `{text}` match exactly, that `css: "text=…"` is Playwright's substring match, and that `index` is supported. |

Done when: each fix has a fixture test that fails on 0.6.0 and passes now.

Progress (2026-11-07, ST-31, branch `ST-31-capture-fixes-for-0-7-0`): all eight items are built.
`tests/capture/capture-fixes.test.js` has one test per fix; all eight failed before the change and pass
now. Capture reports what it changed in `warnings` (skipped optional steps, a highlight moved to
`expect.target`, an omitted caption), and `run-docs` prints them. A specification can set
`captionInImage` once for all its screenshot blocks.

## Backlog after 0.7.0 (not agreed for a release yet)

- **Targets and actions:** `within` scope, name patterns, `hover`, following a new window or tab,
  `scrollTo` a target before a screenshot, network idle except named URLs.
- **Several apps in one module:** a base URL per module or step. Rules with the same id are reported
  with both sources. Rules may list only files.
- **Unattended runs:** `check --read-only` preflight, `readOnly` modules, declared `hide` with a reason
  in the report, screenshot expectations (`notText`, minimum rows).
- **Maintenance:** `regenerate --hooks` on the CLI, translation-key dependencies, partial captures
  merged into one baseline, a per-section report of text that may be out of date, and the captured
  commit recorded.
- **Short artefacts:** scenes, region screenshots, live (non-deterministic) screens.

## Not in AutoTour

Brand values, label texts, product names, demo data, the authoring method for a particular manual, and
the list of which project workarounds each feature replaces. These stay in the consuming projects.
